# 更新与发布

**语言 / Language:** 中文 | [English](updates_EN.md) · [返回 README](../README.md)

## 安装与旧版迁移

源码与正式发行统一在 [WaltomAdaam2/IdentityV-Assistant](https://github.com/WaltomAdaam2/IdentityV-Assistant/releases)。从 0.1.7 起，更新清单、预发布检查和软件内项目链接均使用此仓库。

| 已安装版本 | 迁移方式 |
| --- | --- |
| 0.1.0 | 没有内置更新，手动安装 0.1.7 |
| 0.1.1 | 仅接受早期固定附件名，手动安装 0.1.7 |
| 0.1.2–0.1.6 | 旧 `desktop-releases` 仓库提供一次 0.1.7 过渡更新；安装后使用新仓库 |
| 0.1.7 及以后 | 直接使用本仓库的更新渠道 |

过渡更新使用同一个签名安装包。为兼容 0.1.2 的严格文件名校验，旧仓库额外提供 32 位十六进制文件名，旧清单指向该附件。不能把新仓库清单原样复制到旧仓库。旧仓库删除后，尚未迁移的 0.1.2–0.1.6 用户需要手动安装。历史安装包内部仍保留当时的链接和许可；迁移 Release 不会改变其二进制内容。

过渡版发布并验证后，可以将旧仓库保持公开并归档。归档使仓库及 Releases 只读，保留原名称、标签和附件即可继续向旧客户端提供迁移入口；需要修改时可先取消归档。参见 [GitHub 归档说明](https://docs.github.com/en/repositories/archiving-a-github-repository/archiving-repositories)。

## 软件内更新

默认使用 GitHub 直连（默认），也可手动选择 GH-Proxy、GHFast 或 ghproxy.net。0.1.8 移除自动测速，旧 `auto` 配置会迁移为直连；已手动选定的代理保持不变。启动检查可关闭；发现更新后先展示说明，用户确认后才下载或安装。忽略某版本的启动提醒不会阻止手动检查。预发布开关默认关闭。

安装包必须通过项目/版本地址、发布签名、签名内版本、SHA-256 和大小校验。下载可取消，重试从头开始。下载期间不能关闭更新弹窗，需先取消下载再关闭；校验和安装期间也保持弹窗。安装前停止自动化并释放输入、清理本助手拥有的登录代理，然后退出并启动安装器。本地配置、日志、地图位于 AppData。

助手下载进度右侧显示最近五秒的实际速度和预计剩余时间；刚开始、大小未知或停滞时显示待估算。估算会随网络变化，不包含校验与安装时间。更新日志支持标题、列表、强调、代码与 HTTPS/HTTP 链接；不执行 HTML、脚本或加载嵌入图片。选源同样用于独立登录组件的检查和下载；组件热更新与助手更新是两套流程。

0.1.9 起，登录组件热更新也显示逐模块的已下载大小、可靠的总量和实际速度，小文件使用 B／KB。未知总量不显示虚构百分比；准备、应用文件和恢复代理分别显示阶段。此流程仍使用原官方热更新校验、备份和回滚记录。

组件更新弹窗可选择“不再提醒本批组件更新”。此选项只忽略相同版本、模块和提交的启动提示，新版本或新提交仍会提醒，手动检查始终可用。应用热更新前会确认配置可写，完成后读取磁盘记录核验；记录未保存时会报告失败，不能仅凭下载完成认定更新成功。

## 维护者打包

先完成 [开发环境](development_zh.md) 准备，再从干净且已推送、尚未合并的版本分支（例如 `SNAPSHOT-v0.1.8`） 打包：

```powershell
pnpm install --frozen-lockfile
pnpm tauri build
```

构建会打包 Python 引擎并运行离线自检，不需要游戏或账号。

签名私钥默认位于 `%LOCALAPPDATA%\IdentityV-Assistant\release-keys\updater.key`；也可用 `TAURI_SIGNING_PRIVATE_KEY` 指定原始密钥文件，加密密钥另设 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。脚本不打印密钥、不生成替代密钥。备份原密钥且不要提交或上传；更换密钥会使旧客户端无法验证后续更新。仓库只保存公钥。

`src-tauri/target/release/bundle/nsis/` 中的正式附件：

- `IdentityV-Assistant-<版本>-Windows-x64-Setup.exe`
- 同名 `.exe.sig`
- `latest.json`：版本、说明、附件 URL、签名、SHA-256、大小及构建提交
- `SHA256SUMS.txt`：安装包校验清单

附件必须来自同一次构建。Tauri CLI 2.12+ 将版本写入签名的可信注释；客户端同时验证签名内版本。生成清单并不能替代重新构建，发布者仍须保存实际构建和验证记录。打包不会自动上传。

## 发布步骤与说明格式

1. 从最新 `main` 新建 `SNAPSHOT-v<版本>`（例如 `SNAPSHOT-v0.1.8`），更新所有版本号，检查通过后提交推送该分支，并创建到 `main` 的 PR。
2. 从该干净提交重新构建，核对签名与离线自检结果。
3. 准备 UTF-8 版本说明文件，按照下方说明格式记录真实变化。
4. 在已登录的 GitHub CLI 环境中创建并上传草稿：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/publish_release.ps1 -NotesFile docs/releases/0.1.8.md
```

说明格式：标题、概述、`## 新增与优化`、`## 修复内容`、`**Full Changelog**` 比较链接。脚本将这些完整说明放入清单和 GitHub Release，并在正文最后追加四个附件的 `## SHA-256`。不足三条真实变化时如实少写，初版使用真实历史链接。不要将 SHA 区块提前写入 NotesFile，以免重复或产生清单自引用。

脚本校验版本对应的干净 SNAPSHOT 分支、PR 尚未合并、远端与构建提交一致、版本、附件哈希、大小和签名文本；草稿指向实际源码提交。脚本只创建草稿并上传四个附件，绝不正式发布。若同名标签或 Release 已存在（包括草稿），立即停止，绝不覆盖或删除。网络结果不明确时先检查 GitHub 上已有状态，再恢复操作。

5. 核对 PR、草稿说明、校验值和构建证据。PR 合并后，草稿和签名附件应继续对应已验证的原构建提交。
6. 在 GitHub 手动发布已审核的草稿，并确认正式版设为 Latest。发布前公众和软件自动更新都看不到草稿；发布后的新标签指向已验证的原构建提交。

若先合并 PR、再创建草稿，仍须在合并前从干净且已推送的 SNAPSHOT 提交构建并验证。合并后只能上传这一份原构建，使用 `-MergedPullRequest <PR编号>`：脚本核对已合并 PR 的仓库、版本分支、原提交、main 历史与远端分支未变，再执行原有附件完整性检查。可在该原提交的干净 detached worktree 上传；不得修改或同步已冻结的 SNAPSHOT 分支。此选项不允许覆盖已有标签／草稿，也不允许正式发布。

发布签名是更新校验，并非 Windows Authenticode 签名；Windows 可能显示未知发布者。当前源码和 0.1.7 起的自有代码使用 GPL-3.0-only，历史二进制及第三方材料保留原许可，详见 [第三方声明](../THIRD_PARTY_NOTICES.md)。
